# Interface language and authored content

The interface supports English and Chinese at the existing canonical URLs. `src/i18n/language.ts` resolves a valid saved `ui-language` preference first, then the first supported base language in `navigator.languages` (`zh-TW`, `zh-CN`, `en-US`, etc.), then English. Automatic detection does not write storage. An explicit toggle choice does; unavailable storage falls back to the in-memory nanostore.

`BaseHead.astro` sets `data-ui-language` before paint. `src/i18n/client.ts` owns the nanostore, delegated toggle handler, cross-tab storage/browser-language changes, and translation before SPA swaps and on `astro:page-load`. It does not bind new persistent handlers on every page. The runtime preserves the article document's authored language; translated text leaves have their own `lang` attributes.

## Authoring UI text

Use `data-i18n-en="All posts" data-i18n-zh="全部文章"` on a **leaf** element with English fallback children. The client replaces its text content, so wrap text separately from icons and other children. For an attribute, add `data-i18n-attr="aria-label"` (or `placeholder` / `alt`) and keep the original attribute as fallback. Attribute translations do not replace children.

For real server-rendered alternate fragments, use `data-ui-lang="en"` and `data-ui-lang="zh"`; early CSS and the client hide the other fragment. These fragments must not contain duplicate IDs. For fetched HTML, call `applyLanguage(container)` after insertion. `uiLanguage`, `setUILanguage(language)` and `applyLanguage(root)` are exported from the client module. Do not import this browser-only module from server frontmatter; pure language helpers live in `language.ts`.

## Articles and routes

`getHomePosts()` in `src/utils/postTranslations.ts` groups only verified translation pairs and picks a real counterpart for the preferred language, preserving the original's ordering. Unpaired articles remain visible in either preference. Draft counterparts are excluded. Article bodies, titles, excerpts, tags, personal-page prose and Telegram posts are authored content and are not machine-translated. `/posts` keeps its existing design and All/English/中文 filters independently of this UI setting.

The implementation deliberately does not enable Astro locale routing: there are no `/en/` and `/zh/` page trees, and existing article URLs already identify independently authored versions. Astro's built-in i18n config/helpers manage locale URLs; `Astro.preferredLocale` detection requires on-demand rendering and does not supply a browser preference to prerendered pages. No route redirects, fabricated translations, or fallback rewrites are added. If the site later publishes independently localized page trees, reconsider built-in routing then.

Reference: https://v5.docs.astro.build/en/guides/internationalization/

## Verification

- `node --test tests/ui-language.test.mjs tests/post-translations.test.mjs`
- `tests/home03-i18n.test.mjs` covers Chinese browser detection, saved English preference, home counterpart selection, SPA navigation, reload and mobile toggles against a local server (use the existing browser runner's external-server mode).

No JavaScript: English UI fallback, original authored content and real links remain usable. Early head CSS reduces home fragment flash; ordinary translated labels are updated when the small language module runs. This is interface localization, not localized SEO metadata or automatic translation of third-party comment embeds.

Language controls use the same translation SVG in the desktop header and mobile drawer toolbar. Below 768px only the drawer control is shown. `applyLanguage()` updates its accessible label and tooltip without replacing the SVG. Both controls share the stored preference.
